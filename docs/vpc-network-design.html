Factorial VPC session network

How the builder and reviewer Runtimes keep working once they move to VPC mode in private subnets that reach neither GitHub nor the public npm registry.

Design proposal for Factorial, 30 October 2026, revised 1 November 2026. Region eu-west-1. Not yet agreed: nothing here is binding until it reaches CLAUDE.md.

Recommendation. Give the session subnets no path to the internet at all, and move every GitHub operation into the orchestrator Lambdas, which already hold the tokens and already run outside any VPC. The repository crosses into a session as a git bundle through a short-lived S3 transfer bucket, fetched over the free S3 gateway endpoint with a five-minute presigned URL. Commits cross back the way they do today, as a bundle on the command stream. The clean-room push leaves the builder Runtime and runs inside the Collect Lambda. Packages come from CodeArtifact with an npmjs upstream through its interface endpoints. The model and web search reach Bedrock and the AgentCore gateway through interface endpoints. The NAT gateway is not on the session route table.

  1. No session ever talks to GitHub again, not even with a read token header. The design rule "no credential enters the sandbox" becomes true for GitHub in full.
  2. Nothing reachable from a session accepts a write. The S3 endpoint policy allows GetObject on three buckets and nothing else, so even stolen outside credentials cannot upload through it.
  3. One new container (a Lambda image with git) and one new stack (factorial-network). No new service to run.

Status, 1 November 2026. The VPC itself is deferred: the interface endpoints it needs cost about three times a NAT gateway per month, which the proof of concept does not justify. The parts that stand without it are going ahead in this order: CodeArtifact (#242, deployed and working), the clean room in the Collect Lambda (#261), then the clone handover through the transfer bucket (#262). The Runtimes stay NetworkMode: PUBLIC throughout. Once #262 is in, no session reaches GitHub, and the VPC change reduces to subnets and endpoints.

Decided 1 November 2026: VPC mode is the target, and its trigger is the first private target. The repositories the final Factorial works on are private, and sessions may need private APIs inside an existing VPC. The first makes exfiltration consequential, and only the network stops it by construction; the second cannot be done from PUBLIC mode at all, since a session there has no path to a private address. The rule: PUBLIC mode for public targets while the proof of concept lasts; VPC mode, the egress allow-list and the capability replacements below in place before the first private repository or private API is enrolled. The sections on the existing VPC and on security groups say how the design changes for that.

The design in one picture

The invoker and the orchestration Lambdas stay where they are. They are trusted code, not sandboxes, and they need GitHub, Step Functions, the ledger and the artefact store. Nothing about this design requires them inside the VPC. The invoker keeps its public subnets; moving it into the private subnets later is optional and would need the bedrock-agentcore data-plane, S3, DynamoDB and logs endpoints.

Repository in and out

Today the orchestrator already owns every GitHub call, but two of its scripts run their network traffic inside a session: the fetch that seeds a session (Prepare, ContinueBuild and PrepareReview share cloneScript) and the clean-room push in Collect, which runs in a second session on the builder Runtime. Both move out of the session, and neither needs the VPC: the push first (#261), then the seed (#262). The bundle format already in use for commits leaving a session is the right carrier for commits going in.

What the transfer bucket is

  • Separate from the artefact store. The artefact bucket is write-once, delete-denied and read by no session. The transfer bucket is the opposite: ephemeral, read by a session, expired by a one-day lifecycle rule. Keeping them apart keeps the artefact rules literally true.
  • Keys follow the correlation convention: <workItemId>/<attempt>/<stage>/repo.bundle.
  • Who writes: the Prepare, ContinueBuild and PrepareReview roles, PutObject only. Who reads: the same roles, so they can presign. While the Runtimes are PUBLIC the controls are the five-minute expiry, the unguessable key and the one-day lifecycle. With the VPC, the bucket policy denies GetObject unless aws:SourceVpce is the session VPC's S3 gateway endpoint, and a presigned URL that leaks is useless anywhere but inside those subnets.
  • The URL is consumed by root in the seeding script, before the workspace is handed to the agent user and before any model runs. The bundle file is deleted in the same script. The agent never sees the URL, and it is dead within five minutes anyway.
  • Size. Factorial's own history bundles to under 2 MB, and every target in view is well under 100 MB. The Lambdas get 2 GB of memory and 2 GB of ephemeral storage, and the bundle is streamed to S3 from the file, so disk holds one copy of the pack. A command on the session API is capped at 64 KB, which is why the bundle cannot travel the way the seed files do.

Why the bundle carries full history

  • A shallow clone cannot be bundled. Verified with git 2.56: git bundle create accepts a shallow repository, but cloning from the result fails with "remote did not send all necessary objects". So the Lambda cannot shrink a target by cloning with --depth.
  • A partial clone has nowhere to fetch from. A --filter=blob:none clone in the session would lazily fetch missing blobs from GitHub, which is the path being removed. Today's cloneScript already avoids the filter for the same reason.
  • Full history is what the roles have today. git blame, git log -p and git show on old commits keep working; a missing-object error is a failure mode a model will hit and then fight.
  • Single branch keeps it small. The Lambda fetches only the refs the session uses, the default branch, a rework's base branch when it differs, and the work branch, with no tags, which is often most of a mirror.
  • The reduced form, if a target ever needs it: a clone with a blob size filter (full commit history, large files only at the checked-out commit) carried as a tarball, with lazy fetching switched off, chosen per target in its .factorial/. The outbound base..HEAD bundle imports cleanly from such a clone (verified). Not built until a target needs it; Git LFS targets are a separate question.

The clean room moves into Collect

The push script does not change: fresh bare clone with hooks disabled, import the bundle, check the head is the expected commit and the base its ancestor, refuse merges, re-create every commit under the App's bot identity, push a fast-forward to factorial/*. What changes is where it runs. A Lambda invocation that has never run a model is a clean room by construction. It runs the script with child_process in a fresh directory under /tmp, with the hardened git environment, and removes the directory afterwards. The cleanRoomTarget session and the builder Runtime's involvement in pushing disappear. This is #261, and it goes first: it needs no bucket, it removes a session per item, and it brings in the orchestration image that #262 then uses.

Git in a Lambda

The orchestration functions are esbuild bundles on the managed Node 24 runtime, which has no git. The clean answer is an orchestration container image: public.ecr.aws/lambda/nodejs:24 for arm64, pinned by digest, plus git from the distribution, the bundled handlers copied in. The deploy workflow builds and pushes it next to the invoker and agent images, tagged by a hash of its inputs, and the template switches the functions that run git to PackageType: Image with ImageConfig.Command naming each handler; AutoPublishAlias: live is unchanged. Only the four functions that run git move (Collect in #261; Prepare, ContinueBuild and PrepareReview in #262); the rest stay zips, so the change touches nothing it does not need to. A Lambda layer carrying a static git would also work but drags shared libraries and a second build mechanism along with it.

Packages through CodeArtifact

The builder installs whatever the target's lockfile says, and that is the one place a session must pull from outside AWS. CodeArtifact with an external connection to npmjs is the serverless answer: a repository in Factorial's account, reached through two interface endpoints, that fetches a package from the public registry the first time anyone asks for it and keeps it. It needs no server, it covers pypi, Maven, NuGet and Cargo when other targets arrive, and it keeps a record of every version a session has ever installed.

What changes for the builder

  • The builder execution role, and the agent boundary, gain codeartifact:GetAuthorizationToken on the domain and codeartifact:ReadFromRepository on the repository. sts:GetServiceBearerToken is already granted for ECR Public. The reviewer gets nothing: it installs nothing.
  • The host writes /home/agent/.npmrc before pi starts: the registry URL and _authToken, owned by the agent user, mode 0600. Yarn and pnpm read the same registry setting. The domain and repository names reach the host as Runtime environment variables, like the model ids.
  • Lockfiles that resolve to registry.npmjs.org still install: npm's replace-registry-host defaults to rewriting that host to the configured registry, and the integrity hashes match because CodeArtifact serves the same tarballs.
  • The first install of each package version pays an upstream fetch; after that it is in-region.

An accepted divergence to record. The .npmrc token is the first stored credential in a session. It is tolerable because it is read-only, it reaches a mirror of public packages and nothing else, it expires with the session, and the execution role whose credentials mint it is already reachable from the model's shell today. A prompt-injected builder gains nothing from it that it did not have. Write this into docs/security.md section 7 beside the egress entry it closes. The tokenless alternative, a Verdaccio proxy on Fargate with no authentication, trades a scoped token for a service to run and an open registry inside the boundary, which is worse.

Endpoints, policies and the exfiltration argument

With no default route, the only way out of a session subnet is an endpoint. Every endpoint policy therefore does two jobs: it names what Factorial's roles may do, and it pins the principal to Factorial's account, so that credentials smuggled in through a prompt cannot use Factorial's endpoints to reach an attacker's bucket, repository or gateway. The S3 policy goes further and allows no write at all.

Security groups

  • factorial-session on the Runtime ENIs: no ingress; egress TCP 443 to factorial-endpoints, to the S3 prefix list, and one rule per private API naming that API's security group and port. Never a CIDR, neither the VPC's nor the peer's.
  • factorial-endpoints on the interface endpoints: ingress TCP 443 from factorial-session only.
  • Both roles share the same subnets and both get the session group. A later role that needs less (the verifier Runtime, which may call no model) gets its own group with fewer destinations. Private API rules belong on the group of the role whose work needs them, which is usually the verifier's, not the builder's.

Subnets and routing

  • Two session subnets, one each in euw1-az1 and euw1-az2. AgentCore supports all three eu-west-1 zones; two is the documented minimum for availability.
  • Their route table holds the local route, the S3 gateway prefix and, once the existing VPC is peered, routes to the subnets that hold the private APIs and no others. No NAT, no internet gateway.
  • If account policy insists on a NAT gateway, it lives in a public subnet and nothing routes to it from here. The design does not depend on it.
  • AgentCore creates the ENIs itself through its service-linked role; the execution roles need no EC2 permissions. The CloudFormation execution role must be allowed to create that service-linked role once.

The existing VPC and private APIs

The original draft created a VPC of its own. With private APIs in an existing VPC the choice is between placing the session subnets in that VPC and peering a Factorial VPC to it. Peer. A session is hostile once its agent has run, and VPC mode gives it, for the first time, a network position inside your estate. In a peered VPC the only routes it has are the ones the peering adds, each to a named subnet; in the shared VPC the local route to every address is there from the start and only security groups stand between a session and everything else. The network stack therefore creates the Factorial VPC, takes the existing VPC's id, its API subnets' CIDRs and the API security group ids as parameters, requests the peering, and adds the routes on both sides. The private hosted zones the APIs' names live in are associated with the Factorial VPC so sessions resolve them.

  • Egress is a security group rule per API, on the role that needs it. Each rule names the API's group and port; the API's own group admits factorial-session on that port and nothing wider. Adding an API is one rule on each side and a line in the target's .factorial/ saying its tests need it.
  • The APIs a session may reach are non-production or read-only. A session that reaches a system which accepts writes has a way to act, and the output of a build is a pull request, not an action. If a target's tests need a writable API, it should be a test instance.
  • Shared endpoints are a cost decision, not a design one. A production VPC often already has the logs, ECR and S3 endpoints. The session subnets cannot use endpoints in a peered VPC (interface endpoints are not reachable over peering by default, and private DNS does not cross it), so Factorial's VPC has its own, which is also what keeps their policies Factorial's.
  • The invoker and the Lambdas are still outside. They call the AgentCore API, which delivers into the microVM; nothing about the peering concerns them.

What remains. Two channels are still open to an injected agent: the model itself (it can put anything into a prompt, but the far end is Bedrock in Factorial's account) and DNS, since the VPC resolver answers for any name. Route 53 Resolver DNS Firewall closes the second if it is ever worth the cost. Neither is new; both are smaller than the open egress they replace.

Order of work

  1. CodeArtifact (#242, done): domain, repository, token per run, .npmrc, registry in the environment. Runtimes PUBLIC; npm goes through CodeArtifact over the public endpoints.
  2. Clean room in Collect (#261): foundation redeploy for the ECR repository, the orchestration image, the push in the Lambda, the second session removed. One labelled item and one rework turn.
  3. Seed from a bundle (#262): transfer bucket, fetch and bundle in the Lambda, presigned download in the session script. After this no session touches GitHub. One labelled item, a round 2 and a rework turn.
  4. Replace what the flip removes: a documentation fetch served through the gateway with a domain allow-list (or evidence that web search alone is enough), and a mirror for every registry a private target's lockfiles name. Done while still PUBLIC, so each is verified on its own.
  5. Flip to VPC, before the first private repository or private API is enrolled: foundation permissions for networking and the peering, the network stack, NetworkConfiguration, the aws:SourceVpce condition on the transfer bucket, remove the direct fetch. One labelled item on a public target first, then the private one. Each step is one pull request and reverts cleanly on its own.

Checks before the flip

Each is one call, and each would otherwise be found by a failing labelled item that costs Bedrock money.

  1. Global inference profile through the bedrock-runtime endpoint. AWS documents cross-region inference and PrivateLink separately; the combination is not stated. The eu profiles are still granted to both roles, so the fallback is a one-line change of FACTORIAL_MODEL.
  2. Gateway private DNS. *.gateway.bedrock-agentcore.eu-west-1.amazonaws.com must resolve to the endpoint from a session subnet, and InvokeGateway must succeed through it with the endpoint policy attached.
  3. Command API in VPC mode. Seed a VPC-mode session with the command API and read a file back. The docs describe it as service-delivered; confirm it before the flip, since Prepare and Collect depend on it.
  4. Image refresh with only the ECR and S3 endpoints. Start a session on a fresh version. AgentCore refreshes container images through the VPC and a missing endpoint shows up as a session that never starts.
  5. Token duration. Mint a CodeArtifact token for 14,400 seconds, the builder's MaxLifetime, and confirm it is honoured (the documented range is 900 to 43,200).
  6. npm ci against CodeArtifact with Factorial's own lockfile, which resolves to npmjs. Expect the host rewrite to make it transparent.
  7. The presigned GET succeeds from a session and fails from a laptop once the aws:SourceVpce deny is in place. Until then (#262) it fails after five minutes anywhere.
  8. A private API over the peering. From a session on the role that needs it, one request to the API by its private name succeeds; from the other role's session it is refused; and from a session, any address in the existing VPC other than the named APIs is unreachable.
