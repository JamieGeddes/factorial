# How Factorial works today

The record of what is deployed and how it behaves, stage by stage. `CLAUDE.md` holds what is agreed and binding (requirements, target architecture, what is fixed from day one, the shape of the current stage and the conventions); this document holds the detail behind its **Current stage** section. When a change completes or alters a stage, both are updated in the same pull request.

Stage 0 is complete: on 2026-10-17 a labelled issue (#2) became a tested pull request (#3) with no human step in between. Its agents then moved from AgentCore Harness to the Claude Agent SDK on AgentCore Runtime (`docs/agent-sdk-plan.md`), and from the SDK to pi (`docs/pi-plan.md`): tag `stage-0-harness` marks the last commit with the harnesses, `stage-1-agent-sdk` the first with none, and `stage-1-claude-sdk-final` the last with the SDK. `docs/finding-a-run.md` goes from a work item id to everything a run produced.

## Triggers

- The triggers stack (`factorial-triggers`) holds the `factorial-work` event bus, the webhook secret and the GitHub issue adapter (`packages/triggers-github-issues`) behind a function URL on its `live` alias.
- Factorial acts as a GitHub App (`docs/github-app.md`), created and installed by a human. Adding the `factorial` label to an issue produces a `WorkItem` on the bus; the person who added the label is the requester.
- **Pull request events** (since #22; facts only since #163). The App has one webhook URL, so the same adapter Lambda handles events on Factorial's own pull requests (`pull-request-event.ts`, one pure function `decidePullRequestEvent`). It records what happened and never interprets it: each event becomes a `WorkItem` with `inReplyTo` the pull request, `source.type` saying what the event was and `source.id` its own id, and `body` what was said. A review submitted with "Request changes" is `github-pull-request-review` (its text, possibly empty); an inline comment on the diff whose first token is `@<slug>` (the `GitHubAppSlug` parameter) is `github-pull-request-review-comment`, and such a comment in the conversation `github-pull-request-comment` (the text after the mention); a workflow run that fails on the pull request's head (on `push` or `pull_request`, so the dispatched test workflow never counts), started and re-run only by the App or a trusted person since its logs become the builder's instructions, is `github-workflow-run`. The adapter filters only on what the payload shows: open pull requests by `<slug>[bot]` (from a `factorial/<uuid>` branch in the same repository, where the payload carries the branch), people in `AllowedGitHubUserIds`, never bots, `created` comments only. Which branch, which item opened the pull request and what the event asks for are Intake's to decide (see Intake). Ignored events are logged with the reason.
- **Closed pull requests** (#204). A `pull_request` event with action `closed` on a pull request by `<slug>[bot]` from a `factorial/<uuid>` branch in the same repository becomes a `PullRequestClosed` event (source `factorial.triggers`, `contracts/pull-request-closed/v1/`, validated by `@factorial/pull-request-closed`): the repository, number, URL, head branch, `merged`, `closedAt`, and for a merge `mergedAt` and the merge commit, and who merged or closed it. It is a fact, not a request: it never becomes a `WorkItem` and never reaches Intake (see The thread outcome). Every other `pull_request` action is ignored and logged.
- The `WorkItem` contract (`v2`) is in `contracts/workitem/v2/` (JSON Schema, with the event envelope and change process in `contracts/workitem/README.md`), validated by `@factorial/workitem`, which still reads `v1` items until they have drained. The adapters emit `v2`. It carries optional lineage: `group` (`id`, `size`, `index`: the items one trigger produced) and `parentId` (the item whose Plan stage emitted it). Intake copies them onto the ledger row as `groupId`, `groupSize`, `groupIndex` and `parentId`, and `groupId-createdAt-index` and `parentId-createdAt-index` list a group's or a parent's items. Nothing produces or reads them yet.

## The state machine

The orchestration stack (`factorial-orchestration`) holds the `factorial-work` state machine (Intake → Route → Prepare → Build → Collect → Test → PrepareReview → Review → CollectReview → OpenPullRequest, with Build → SaveWork → ContinueBuild → Build when the builder runs out of steps) behind its `live` alias, the bus rule that starts it, the `factorial-work-items` ledger, the `factorial-threads` table, the Fargate invoker (`packages/invoker`), the orchestrator Lambdas (`packages/orchestration`) and the artefact store. Every state's output carries `workItemId` and `attempt`.

### Intake

Intake (`functions/intake.ts`, since #163) accepts the item exactly once (the ledger row is the idempotency guard; a duplicate ends in `Duplicate`), resolves the **thread** it is a turn in, and chooses its **route**; the Route choice runs Prepare for `change` and ends in `NotAdmitted` for `refuse`. It records `executionArn`, `route` and `threadKey` on the ledger row and writes `intake/intake.json` (`contracts/intake/v1/`, validated before it is stored or returned). No session is touched. `docs/design-extension-points.md` §3 is the design.

- **Threads.** The `factorial-threads` table holds one row per branch Factorial works on (`threadKey`, `<owner>/<name>#<branch>` with owner and name in lower case): the item that created it, the source it came from, the pull request once one is open (`pullRequestKey`, `prNumber`, and `prOpenedBy`, written by OpenPullRequest), what became of it (`outcome`, #204), which turn holds it (`inFlight`), the automatic reworks since a person last asked and whether the limit was announced, and a `version`. Pointers and counts only. Each work item row carries its `threadKey`, and `threadKey-createdAt-index` lists a thread's turns.
- **Turns on a pull request** name it through `inReplyTo` (`lib/turn.ts`), and the cause is derived from the source type (`github-pull-request-review` and `-review-comment` are `review`, `-comment` is `comment`, `github-workflow-run` is `checks-failed`); an unknown type is refused as `not-eligible`. An item in the superseded rework `context` shape is refused as `not-eligible` too: nothing emits it since #163, and nothing reads it.
- **A new request** opens a thread for a new `factorial/<workItemId>` branch. **Resume:** a new item from the same source as an earlier attempt that failed after saving work, or whose tests failed, resumes on that attempt's thread and branch. Intake finds the newest thread the source opened (the threads' `sourceKey-createdAt-index`) and walks the source's own turns on it (`threadKey-createdAt-index` on the work items); attempts made before threads (#163) are not found. Prepare adds a "Previous attempt" section to the notes; the builder's first message also says the attempt resumes and to build on the branch's commits. A resumed item's attempt is one more than the attempt it resumes, and its artefact prefix uses its own id.
- **A turn on a pull request** finds the thread through the threads' `pullRequestKey-index`. A pull request with no thread recording it is `not-eligible`. The thread policies (`lib/thread-policy.ts`) then apply, in order: the pull request, read from GitHub, must be open, by the App, from this repository and headed by the thread's branch (else `not-eligible`); an item from an inline comment that belongs to a review requesting changes is refused, since that review's own item takes all its comments (else `covered-by-review`); the turn holding the thread must have reached a terminal status or be over 8 hours old (else `busy`); and a `checks-failed` turn is refused after two admitted in a row with no turn a person asked for between (else `rework-limit`). Admission claims the thread with one write conditional on its `version`, re-reading up to three times, so of two turns that arrive together exactly one runs. Nothing releases a claim: the holder's ledger status says when it has finished. An admitted turn from a comment gets an eyes reaction on that comment, so the person sees it was taken. A refusal is recorded with `refusedReason` and in `report.json` and ends the turn with a `refused` outcome; the GitHub reporter answers it on the pull request when a person asked (`busy` for a review or a request; `rework-limit` once, recorded on the thread).

### The seed

What a session starts with is assembled in one place (`lib/seed.ts`, #166; design in `docs/design-extension-points.md` §3.6). A **provider** is a function from the seeding context (the item, the branch head and base branch, the stage's own inputs such as the stored plan) to **files** for `/workspace`, each with a byte cap, and **sections** for the first message. A stage lists its providers in order in its handler, and `assembleSeed(providers, context)` runs them one at a time, so the result is deterministic and the numbering of a rework's points holds in every session. It refuses a file name that is not a plain name under `/workspace`, a name seeded twice (unless a later provider appends to the first), a file over its cap (prose is cut with a note, JSON is refused) and a section over its cap.

| Provider | Files and sections | Where it reads from |
|---|---|---|
| `requestProvider` | `workitem.json` | the WorkItem |
| `notesProvider` | `notes.md`: the request under `# Task`, the plan and notes headings for the role, the previous attempt of a resumed item | the WorkItem |
| `roundNotesProvider` | `notes.md` of a later round: the previous round's notes (the starting notes if lost) and the "Continuing" section | the artefact store |
| `reworkProvider` | `rework.md`, the points of a rework and the failing jobs' logs | GitHub, with a read-only token outside the session |
| `planProvider` | `plan.json`, `plan.md` | the artefact store, validated |
| `summaryProvider` | `summary.md` | Collect's result |
| `diffProvider` | `diff.patch`, three-dot against the base branch, made in the session and cut at 5 MiB | the clone |
| `sensitivePathsProvider` | section `sensitive-paths` | rules computed by PrepareReview from the base branch |

The lists: Prepare `requestProvider`, `notesProvider`, `reworkProvider`; ContinueBuild `requestProvider`, `roundNotesProvider`, `planProvider`, `reworkProvider`; PrepareReview `requestProvider`, `notesProvider`, `reworkProvider`, `planProvider`, `summaryProvider`, `diffProvider`, `sensitivePathsProvider`. Adding a context is a provider function and an entry in a list; `lib/seed-providers.test.ts` shows it with a test-only provider added to a copy of a list.

`placeSeed` is the one writer: after the clone, one hardened script (content base64-encoded, a command's output cut to its cap) writes every file, before `handOverWorkspace`; the clone script only clears the session's files and fetches the repository (see Prepare). Nothing else writes into `/workspace` before a session starts. The first-message sections still reach the invoker through the state and the task's container overrides (PrepareReview's `sensitivePathsJson`, capped at 4 KiB; overrides are capped at 8 KiB in total); anything that can grow is a file. The Runtime request carries only the prompt. The snapshot test `lib/seed-snapshot.test.ts` holds the files and sections seeded for a new item, a resumed item, a rework item, a later round and the reviewer, and `lib/seed-script.test.ts` runs the real writer script with bash against a temporary git repository (quoting, caps, the diff against the base ref).

### Prepare

- Puts the builder's session on the thread's branch (a new branch for a new request, the existing one for a resumed attempt or a turn on a pull request), hands `/workspace` to the `agent` user, and seeds it (see The seed) with `/workspace/notes.md`, holding the request under `# Task` (compaction may summarise the conversation, and the notes file is what a later session starts from).
- **Fetch, not clone** (`cloneScript`, #78): `git init`, `git ls-remote --symref` for the default branch, then one `git fetch` of only the branches the session uses, at full depth: the default branch, a rework's base branch when it differs, and, for an existing branch, the work branch. It then sets `refs/remotes/origin/HEAD` by hand, so `origin/HEAD`, `origin/<base>` and the merge base for the three-dot diffs are all there and no history is truncated; other branches are not fetched. No lazy filter (`--filter=blob:none`) is used: the read-only token is sent as `http.extraHeader` on the network commands only and is written to no file or config, so git could not fetch a missing object later. PrepareReview and ContinueBuild use the same script. The clean-room clone in Collect keeps its own `--filter=blob:none`, since the token is present for that whole script.
- **Rework.** For a turn on a pull request, Prepare uses the pull request's actual base branch and writes `/workspace/rework.md` with the points as numbered sections (the item's details, with an inline comment's file and line fetched when the item names only the comment; then, for an item from a review, the review's inline comments, fetched because the webhook does not carry them; bots left out; at most 50) and, for failed checks, the failing jobs' logs (last 200 lines, redacted, fetched with a short-lived `actions: read` token outside the sandbox). The previous work item in `rework.md`, `reworkOf` and the context's `rework` is the thread's `prOpenedBy`, never the adapter's guess. The builder is told to address each point on the existing branch and to answer each by its number under `## Rework points` in `summary.md` (`- <n>: <how it was handled, or why not>`). Every session seeded for the item (later build rounds, the reviewer) rebuilds the same file. The context carries who raised each point and where (`reworkPoints`) for the reply.

### Build

- **Planning** (since 2026-10-25, `docs/agent-sdk-plan.md` phase 3.1; a separate planner harness and the Plan and CollectPlan states before). The builder first runs its `plan` subagent (read, grep, find, web search, the fetch tool, and write for the two plan files only, enforced by the tool rules; 40 turns; the builder's model), whose prompt is ported from the planner harness's. The subagent writes `/workspace/plan.json`, the plan the builder follows (steps in order by `id`, each with files and a verification; tests to run and add; risks; open questions; optional `followUp` for work that belongs in a separate item; contract `contracts/plan/v1/`, validated by `@factorial/plan`), and `/workspace/plan.md`, its explanation for humans. The host checks `plan.json` after each write or edit to it and sends the errors back to whoever wrote it, normally the subagent; after the second invalid plan every further tool call is denied and the run ends. The stop check will not let a run end without a valid plan. These spare a wasted build; Collect is the gate. Subagents and commands run in the foreground, a command's default time limit being 10 minutes: on #125, on the SDK, the plan subagent ran in the background while the builder slept waiting for it.
- The builder (`factorial_builder`, an AgentCore Runtime with role `factorial-agent-builder`; see Agents) follows `plan.json` step by step, commits after each coherent step, keeps running notes in `/workspace/notes.md`, and writes `/workspace/summary.md` with a `## Plan steps` section reporting each step by its `id`. Its prompt sets an exploration budget before the first edit, forbids installs for documentation-only changes, states once that GitHub belongs to the orchestrator, and keeps the builder to executing the request.
- When a round starts with a plan (a later round), the host appends `plan.json`'s steps (id, description, files, verification) to the builder's first message, so following the plan does not depend on the model opening the file.
- If the builder's `summary.md` lacks a `## Plan steps` line for any step id in `plan.json`, the host's `Stop` hook sends it back to write them, at most twice.
- The Fargate invoker runs each agent to completion and Step Functions waits on it (`ecs:runTask.sync`). It takes the role and where it runs from the state machine's container overrides and passes the ids in the `baggage` header. For each role (`TARGET=runtime`) it calls `InvokeAgentRuntime` on the role's `live` endpoint with a `run` request and reads the host's SSE stream; if the stream ends without a result it re-attaches from the last message number it holds, and the host's `status` gives the final outcome.
- A builder that stops at a turn, budget or time limit (outcome `incomplete`: `max_turns`, `max_budget`, `max_duration`) is incomplete: the invoker ends the round's `Build` entry as failed with the reason and exits with code 3, so a half-finished change is never tested or opened as a pull request. Outcome `complete` (`completed`) is complete; a `failed` outcome is an error. The outcome and reason come from the run's `run.ended` event (`contracts/run/v1/`); before 2026-10-28 `stopReason` held the Claude Agent SDK's result subtype (`success`, `error_max_turns`, `error_max_budget_usd`, ...).
- Session commands on the Runtime run as root through the command API, so the orchestrator hands `/workspace` to the `agent` user after its last seeding write, and every command after the model has run (Collect's inspection, leftover commit, bundle and file export) drops to `agent` with the host's own restrictions (`setpriv`, no new privileges, empty bounding set).
- **Rounds.** A builder session has turn, budget and time limits, so a plan can outlast it. When the builder is incomplete, SaveWork pushes its work and, instead of reporting failure, ContinueBuild seeds a fresh builder session (`<workItemId>-r<round>` on the same Runtime) at the branch head (or the start commit when the round committed nothing) with the plan read back from the artefact store and validated again (none when the previous round ended without a valid plan, and the section then says to plan first), the previous round's `notes.md` (stored by Collect before the push) and a "Continuing (round N)" section: what is on the branch, the `git log` and `git diff --stat` to run, check each plan step against the commits, carry on from the first step not done. The builder runs again with `BUILD_ROUND` set, and its prompt says to read that section first. Rounds repeat until the builder finishes or `MaxBuildRounds` (3, a template mapping; 6 before the spike) is reached, when the item is reported incomplete ("in N sessions") with the saved branch. The branch and `notes.md` are the memory between rounds; nothing is read out of the old session. There is no limit on a work item's size beyond that.

### Collect and SaveWork

- Collect first reads the builder's plan: only `/workspace/plan.json` and `/workspace/plan.md`, as the `agent` user, at most 64 KiB each, redacted; it validates the JSON, stores both with `plan/validation.json`, and records the plan's size (`planSize`: steps, distinct files, description characters, follow-up items) and `planSteps` on the ledger row beside the builder's usage. A build that ends without a valid plan pushes nothing and ends with `invalid-plan` (`planErrors` on the row), reported on the issue. SaveWork stores the plan whatever its state and saves the work regardless. There is no limit on a plan's size beyond the contract's 30 steps.
- Collect inspects the builder's session (hostile once the agent has run), commits anything left uncommitted, stores the session's files, and bundles the new commits. The push happens from a pristine clone in a separate clean-room session with hooks disabled and the token sent as a header; every commit is re-created with the App's identity, and the push is always a fast-forward on top of the head the session started from, never a force push. Collect stops the clean-room session as soon as the push returns and the builder round's session just before it returns, in normal and salvage mode (`StopRuntimeSession`, granted to the orchestration role on both Runtimes, #201). It never stops in a `finally`: a failed Collect leaves the session running for the state's retry, and falls back to the idle timeout. A failed stop (a missing session counts as stopped) is logged with the work item id and never fails the stage.
- When the build stops (a model or API error, the invoker task stopping, or the builder running out), SaveWork runs Collect in salvage mode with the Build failure and the round's session id: whatever the agent committed, plus any uncommitted changes in a commit marked as saved work in progress ("when the builder reached its limit" for an incomplete round, "after the build failed" otherwise), is pushed to the work branch, and Collect reports `incomplete` when the stop was the builder's own limit. Collect also counts the work item's commits over every round (`itemCommitCount`, from the item's base commit), which the failure comment shows; a round's own count said "1 commit" for #78's branch of 4. An incomplete build continues in another round (see Build); any other failure, or the last round, is reported: no tests run and no pull request is opened, the failure comment links the branch, and relabelling the issue resumes from it.

### Test

- The test workflow (`test.yml`) is dispatched on the default branch, so its definition is always the trusted one. The work commit is checked out as data in a job without credentials; a separate job reports the result through a Step Functions task token, assuming the test callback role (its ARN is the `AWS_TEST_CALLBACK_ROLE_ARN` repository secret). A failed run ends the item as `tests-failed`, reported on the issue with the branch left for inspection.
- The callback role trusts only Factorial's own OIDC subject, so this gate works for Factorial alone (#91). #167 replaces it with a Verify stage that runs the checks the target declares in `.factorial/verifiers.json` in a session Factorial owns, on a verifier Runtime with no model or artefact access, and retires `test.yml`, the callback role and the repository secret. Until that lands, this section describes what runs.

### PrepareReview, Review and CollectReview

- PrepareReview clones the pushed branch into a fresh reviewer session, checks that its head is the tested commit, and writes the validated `plan.json` and `plan.md` (read back from the artefact store), the builder's `summary.md` and `diff.patch` (three-dot against the base branch). It also computes the pull request's facts in that session, before any agent runs there: contract and test-file paths, dependency changes (every changed `package.json`, licences as the root lockfile at the pushed head states them, which the body labels as the lockfile's claim) and deploy impact from the base branch's `.factorial/pr-body.json` (`deploy.paths` and `deploy.humanSteps`, each `{prefix, note}`; absent or invalid means "not determined"). They travel in the state as `prFacts`, capped at about 6 KB.
- Before the reviewer runs it works out which changed files are sensitive: built-in rules that hold for any repository on GitHub (Actions workflows and composite actions, `CODEOWNERS`, any `.gitattributes`, `.factorial/`) plus the target repository's own rules in `.factorial/sensitive-paths.json` (exact paths, prefixes, file names and diff content patterns, each with a reason; contract in `contracts/review/v1/sensitive-paths.schema.json`). The rules file is read from the base branch, never the branch under review, so a change cannot loosen the rules that judge it; an invalid file is logged and stored as `rulesProblems`, and the built-in rules still apply. Rename detection is off and diffs are forced to text without textconv, so a moved file is caught under its old path and a branch's `.gitattributes` cannot hide lines. Factorial's own rules (the foundation template, permissions boundaries, the workflow and change-classification checks) live in its `.factorial/sensitive-paths.json`, not in the code.
- The reviewer (`factorial_reviewer`, role `factorial-agent-reviewer`) judges the change against the request and the plan, treating everything it reads as untrusted, with the flagged files and their reasons in its prompt, and writes `/workspace/review.json` (verdict, four scores from 1 to 5, findings, summary; contract in `contracts/review/v1/`, validated by `@factorial/review`). Its prompt has it write the review early and refine it, and the host's `Stop` hook sends it back, at most twice, while `review.json` is missing or invalid, and sends the first valid review back once for a second pass over the callers, the tests and, for a data or configuration file, its schema and the code that reads it (#147, #149 and #150's reviews read only the diff and stopped, with or without the prompt asking for more). PrepareReview hands `/workspace` to the `agent` user after its last command, and CollectReview reads `review.json` as `agent`.
- CollectReview reads only `review.json` out of the session (at most 64 KiB, redacted), validates it and adds a high-severity finding for every sensitive change, whatever the reviewer wrote about it. CollectReview stops the reviewer's session just before it returns (not when it throws; a failed stop is only logged). The review is advisory: the PR body shows the verdict, scores and findings, and if any review step fails the PR still opens, saying the review did not complete. The ledger holds the reviewer's run under `review` and the result as `reviewVerdict`, `reviewScores` and `reviewFindings`.

### OpenPullRequest and Report

- OpenPullRequest verifies the branch head is the tested commit and opens the pull request, whose body `pr-body.ts` builds as seven fixed sections: Summary, Impact, Review focus, Automated review, Tests, Plan (departures only, read from the builder's `- <id>: done|skipped|changed: <why>` lines; the full list, with descriptions read back from `plan/plan.json`, is collapsed) and Run details (collapsed table with the artefact prefix). Facts come from `prFacts`, the test result, the plan and the review; the builder's `summary.md` sections fill only their own slots, redacted, capped and with a placeholder when missing. Values the branch controls (paths, package names, versions, licences) appear only as code spans, so they cannot add Markdown or close the collapsed blocks, and agent-written text cannot mention anyone (a zero-width space follows every `@`). Run details include a Branch row (the trigger adapter read it back before #163; the thread holds the branch now). Every terminal path writes `report.json` and emits the turn's outcome (see Outcomes and the GitHub reporter); OpenPullRequest and Report post nothing themselves. When no pull request follows (no changes, tests failed, invalid plan, or a failure, with the saved branch linked) the reporter says so on the issue.
- **Rework results** (since #24). A rework item's branch already has a pull request, so OpenPullRequest runs the same head checks and then, instead of opening another, records it as updated, and the reporter replies on that pull request: each point, numbered as in `rework.md`, with the builder's `## Rework points` answer beside it (or a placeholder), then the summary, the automated review and the tests for the new head, and the run details; `pr-body.ts` builds it from the facts in `report.json` and the description is left as first opened. A `comment` rework is answered as the requester's ("after the request from @…", under `## Request`) and re-requests nobody. For the `review` cause the reporter re-requests review from the distinct people who raised the points (never a bot; a refusal is logged, not fatal). The ledger status is `pr-updated`, and `pr/pr.json` and `report.json` say so. A rework that opens nothing is reported on the pull request rather than the issue, saying what the branch now holds: Collect pushes rework commits straight to the pull request's branch before Test, so failed tests or saved work in progress are on the pull request, untested or failing, and the comment says not to merge.

## Agents

- **Roles are manifests** (#164). `@factorial/roles` (`packages/roles/`) holds what the host, the invoker and the orchestrator share about each role: its stage (artefact folder and log stage), ledger statuses, models by purpose, whether an early stop is incomplete (`mustFinish`), whether it works in rounds, where the ledger keeps its outcome, the `# Plan` section of its starting notes and its first message. The orchestrator finds a role's Runtime in `<ROLE>_RUNTIME_ARN`. The host's own parts of a role (system prompt, tools, subagents, hooks) are in `packages/agent-runtime/src/roles.ts`, because only the host's copy is fixed on the Runtime version. A test in `@factorial/roles` fails on a role conditional anywhere else. The template keeps one Runtime block per role.
- **Builder** (`factorial_builder`, since 2026-10-25; on the Claude Agent SDK under `docs/agent-sdk-plan.md` until spike #181, on pi since, `docs/pi-plan.md`; results in `docs/harness-vs-runtime.md`, **Spike results** and **pi spike results**). An AgentCore Runtime from the `agent-runtime/` image (Node 22, git, gh, jq, ripgrep, `quiet`, python3, and cfn-lint at CI's version) running Factorial's host process (`packages/agent-runtime/`) around pi (`@earendil-works/pi-coding-agent`, MIT, pinned at 1.4.0). pi runs the loop in the host, which is root; every tool that runs a command or touches a file runs as the `agent` user (`docs/security.md` §9.2). The host streams the run to the invoker as run events (`contracts/run/v1/`, since 2026-10-28): its adapter, `src/pi/events.ts`, is the only code that reads pi's events, so the invoker knows neither the harness nor the model's provider. Each Runtime version declares the contract its host speaks (`FACTORIAL_RUN_CONTRACT`), the invoker checks it before invoking and names it in the `run` body, and either side refuses a mismatch before any model call. Each role's prompts, tools, subagents and policy (the tool rules and the plan, report and review checks below) are defined in harness-neutral terms in `src/roles.ts` (#184), and `src/pi/` maps them onto pi: the policy is one host extension (`tool_call` before each call, `tool_result` after each write or edit, `agent_before_settle` before the run may end), and subagents are child sessions behind the `task` tool. `FACTORIAL_EFFORT` fixes the reasoning effort: `high` on both roles (pi's default is `medium`). pi retries a failed model call 10 times, as Claude Code did, doubling the wait from 2 seconds to 60 (`PI_SETTINGS`); its own default of 3 would end a run at one burst of Bedrock throttling. pi's own Bedrock auth looks only for a credential source named in the environment, which the Runtime does not set, so #166's first pi run failed before any model call; the host registers pi's Bedrock provider with its auth falling back to the AWS SDK's default chain (`pi/bedrock.ts`), and requests stay SigV4-signed with the execution role. At a turn or budget limit pi reports the turns the run was allowed and no `detail`: the model call the stop cut off is not counted, and its `error` ending is not pi's (#181's run (b) showed 11 turns and `detail: "error"` at 10). `pi/loop.test.ts` drives pi's loop with its faux provider at both limits, at an abort and through the reviewer's stop checks, and `scripts/pi-security-probe.ts` checks the privilege drop and policy in the image for each role. The run's transcript and result are kept in root-only `/var/lib/factorial`.
- The models are fixed on the Runtime version and named by purpose: Claude Sonnet 5.5 for the main loop, Haiku 5.5 for the read-only `explore` subagent (30 turns) and the fetch tool's answers from a page; the `plan` subagent inherits Sonnet, all through the global inference profiles on Bedrock (the EU ones until 2026-10-28; requests may be served in any commercial region, accepted for the proof of concept, #181). The execution role may call only those profiles, and the EU ones until no session runs on a version that names them; there is no model key. Limits, also on the version: 150 turns, $5 and 6,600 seconds (below `BuildTimeoutSeconds`), set from the spike.
- The tool rules deny file edits outside `/workspace` and `git push`, `gh auth` and `gh api`; they constrain a prompt injection and are not the access gate. Compaction is pi's, as the context nears the model's 1M-token window; no run has reached it yet (the largest peaked at 116k). Web search is the host's in-process `web_search` tool, which signs calls to the `factorial-web-search` gateway with the execution role. `usage.json` records the Runtime version serving `live`, the models, the limits and, in its `harness` block, the harness and its version, the models by purpose, the harness's cost at list price and per-model totals, and each subagent run (type, duration, tool calls, and tokens summed from its own calls, output as a lower bound) with a total per type, which the run's own totals already include. A subagent's final context is kept as `finalContextTokens` (on the SDK, an Agent result's `totalTokens` was only that). Before 2026-10-28 the block was `sdk`, with `resultSubtype`, `numTurns`, `modelUsage` and `permissionDenials`; they are now `detail`, `turns`, `models` and `deniedToolCalls`.
- The builder's prompt names no repository's paths or commands (#91): the builder finds how the target installs, builds and tests from its own docs, and treats documentation-only changes as needing no install. `quiet`'s report picks out failure lines from node:test, TAP, npm, pytest, Go, Cargo and Maven output, and ignores summaries that count no failures.
- **Platform version.** Both Runtimes are on AgentCore Runtime V2 (`PlatformVersion: V2` in `templates/agent.yml`; rollback is `V1`). Each new session is restored from a snapshot taken once per Runtime version, so cold starts are shorter. The host stamps `/ping`'s `time_of_last_update` at the first ping after restore, not at module load. Promotion waits for the `live` endpoint to be `READY`, as V2 prepares a snapshot for the new version, which takes minutes.
- **Session lifetime** (#201). An idle session still holds its memory, which is most of the AgentCore bill, so Collect and CollectReview stop the sessions they have finished with (above) and `IdleRuntimeSessionTimeout` is the fallback, 300 s on both Runtimes (it was 900; AgentCore's minimum is 60; `MaxLifetime` is unchanged). It has to cover the longest idle gap in a run: Prepare's last command to the invoker's first call, which is the Fargate task start (not yet measured; 300 s is a margin, not a measurement), plus the state retries (at most 2 s + 4 s). Build exit to Collect is immediate, and a session that reports `HealthyBusy` is not idle.
- **Reviewer** (`factorial_reviewer`, since 2026-10-26; `docs/agent-sdk-plan.md` phase 3.2; on pi since 2026-10-30, `docs/pi-plan.md` phase 3). A second AgentCore Runtime from the same image and host, with `FACTORIAL_ROLE=reviewer` and role `factorial-agent-reviewer`: its own system prompt (ported from its harness), Claude Sonnet 5.5 for the loop and Haiku 5.5 for background calls, no subagents and no web search. Tools: read, grep, find, bash, and write and edit, which the tool rules let reach only `/workspace/review.json`; the rules also deny shell commands that redirect to a file, commit or otherwise change git state, install, or write with `tee`, `sed -i`, `rm` and the like, and the `bash -c` style wrappers that would hide one. Limits: 60 turns, $2 and 900 seconds (below `ReviewTimeoutSeconds`). Its harness (GLM 5.3 Flash via Z.ai through LiteLLM) was removed with the model key's credential provider the same day, and the `factorial/zai/api-key` secret in phase 4.
- The deploy workflow tags each image with a hash of its inputs, builds it only when that hash is new, and passes the tags to the agent stack.
- The template is laid out one block per role (see **Agent roles** in `CLAUDE.md` Conventions). The deploy workflow's final step moves every runtime's `live` endpoint to its newest READY version.

## The artefact store and the ledger

The artefact store (`factorial-work-artefacts-<account>`, in the orchestration stack) keeps each run's record under `<workItemId>/<attempt>/`. The ledger row holds `attempt` and `artefactPrefix`, and the pull request body links the prefix. The store is write-only, with three read exceptions by the orchestrator: the plan files (PrepareReview and ContinueBuild), the previous round's `build/notes.md` (ContinueBuild) and `report.json` (the GitHub reporter).

| Key | Written by | Contents |
|---|---|---|
| `workitem.json`, `intake/intake.json` | Intake | The work item, and its thread and route |
| `prepare/branch.json` | Prepare | The branch and the commit it starts from |
| `plan/plan.md`, `plan/plan.json`, `plan/validation.json` | Collect (SaveWork too; the latest round's) | The builder's plan, valid or not, and its validation; the plan subagent's run is in the build transcript (`plan/transcript.jsonl` and `plan/usage.json` are the planner harness's, before phase 3.1) |
| `build/transcript.jsonl`, `build/usage.json` (round 1), `build/round-<n>/transcript.jsonl`, `build/round-<n>/usage.json` (later rounds) | Invoker | Every run event (`contracts/run/v1/`; the raw SDK messages before 2026-10-28), redacted, capped at 50 MB with a truncation marker, and the usage: summed and per-call tokens, runtime version, model id, stop reason, tool calls, duration; written on every exit including a stopped task (`stopReason: "interrupted"`) |
| `build/round-<n>/continuing.json` | ContinueBuild | The round's session id and the commit it started from |
| `build/summary.md`, `build/notes.md`, `build/rework.md`, `build/logs/<name>`, `build/logs/index.json`, `build/bundle.git` | Collect, before the push (SaveWork too; the latest round's) | The session's files; command logs 5 MB per file keeping the end and 50 MB in total, with the index listing what was stored, truncated or skipped |
| `test/result.json` | OpenPullRequest, or Report when tests fail | The test outcome and run |
| `review/prepared.json` | PrepareReview | The tested head, changed paths, the rules applied and the sensitive paths |
| `review/transcript.jsonl`, `review/usage.json` | Invoker | The reviewer's run |
| `build/live/<n>.jsonl`, `build/round-<r>/live/<n>.jsonl`, `review/live/<n>.jsonl` | Invoker, while the run goes on | Catch-up chunks for the live feed (#194): the transcript lines since the last chunk, every 200 events or 30 seconds and at the end, each key written once |
| `review/review.json`, or `review/error.json` and `review/review.raw.json` | CollectReview | The review with the orchestrator's findings added, or why there is none |
| `pr/pr.json` | OpenPullRequest | The pull request (`rework: true` when it replied on an existing one) |
| `report.json` | Every terminal path: Intake on a refusal, Report, OpenPullRequest | The outcome and a short reason, and `delivery`: the facts the reporter builds its comment from (`lib/report-file.ts`) |
| `outcome/outcome.json` | The same, through `lib/outcome.ts` | The turn's `Outcome` (`contracts/outcome/v1/`): pointers only |

The ledger row holds `buildUsageTotal` (usage summed over build rounds, which a later round adds to); each run's own figures and record keys are on its stage's entry (below). Token usage keeps the shape it had under the Harness: `inputTokens` is the gross prompt size including cache reads and writes, and `uncachedInputTokens` is what is billed at full rate.

### The progress record

Since #15 the row also holds `stages`: one entry per stage the state machine ran, keyed by the state's name (`Intake`, `Prepare`, `Build`, `SaveWork`, `ContinueBuild`, `Collect`, `Test`, `PrepareReview`, `Review`, `CollectReview`, `OpenPullRequest`, `ReportNoChanges`, `ReportTestsFailed`, `ReportInvalidPlan`, `ReportFailure`), with `#<round>` after the first build round for `Build`, `SaveWork` and `ContinueBuild`. Each entry holds `startedAt`, `endedAt`, `outcome` (`succeeded` or `failed`) and, where they apply, `round` and `error` (a name and a redacted message of at most 1,000 characters). The end of `Build` and `Review` also holds `run`: the role, Runtime name and version, run contract, harness name and version, model, reasoning effort (`FACTORIAL_EFFORT`, now read from the version and also in `usage.json`), session, tool calls, turns, duration, stop reason, outcome, usage, the harness's cost estimate (`costUsd`, at list prices and not a bill, rounded by the invoker to 4 decimal places, a hundredth of a cent, in `usage.json`, the stage entry, the progress events and the `run ended` and `agent finished` log lines; the run contract carries the host's unrounded figure, and any total adds the rounded ones) and the record keys. The row's `endedAt` is set when the item ends.

Every transition is also a `WorkItemProgress` event (source `factorial.progress`, `contracts/progress/v1/`) on `factorial-work`, and the item's end is one more (`stage: "WorkItem"`, `transition: "ended"`, with the final `status`). `@factorial/progress` writes both, the ledger first; each write is conditional, so a retried task writes nothing twice and puts the same event again with the same `eventId` (at least once; subscribers drop repeats). Recording is best effort: a failure is logged as `progress not recorded` and never fails the stage.

- The state machine passes each task its own state name and the build round (`progress` in each Lambda's payload, `STAGE` for the invoker). The orchestrator Lambdas record through `staged` (`lib/progress.ts`), which wraps each handler as `logged` does: the stage starts when the handler is called and ends when it returns or throws. Intake starts its stage only once it has accepted the item, so a duplicate records nothing. Test starts when DispatchTests dispatches the workflow and ends in the next state: PrepareReview records a pass, ReportTestsFailed a failure. SaveWork ends its round's Build, and CollectReview a failed Review, when the invoker could not (a task that never started, or was killed). OpenPullRequest ends the item when it succeeds, every Report state always, and Intake on a refusal; any stage still open is then ended as failed with the error that ended the item.
- The invoker records Build and Review: started once it has read the row, ended in the same place it records its outcome, whichever way the run ends.
- Only the orchestrator emits: the Lambdas and the invoker task role hold `events:PutEvents` on the bus for source `factorial.progress` alone (`factorial-progress-events`). No agent role can: the agent permissions boundary allows no EventBridge action.
- An execution started before #15 passes no stage, so its remaining stages are not recorded. A row accepted before #15 gets `stages` on its first stage write.
- What became of the pull request an item opened is one more event (#204): `stage` `PullRequest`, `transition` `merged` or `closed`, `eventId` `<prOpenedBy>:PullRequest:<merged|closed>`. Its record is the thread's `outcome`, not a stage entry, and `factorial-thread-outcome` emits it (see The thread outcome).
- The GitHub reporter (#165, below) reads the events for the started notice, and the live feed's forwarder (#194, below) publishes them.
- Since the second part of #15 the run is recorded only on its stage's entry. Rows written before it also hold the interim fields: the builder's at the top level (`stopReason`, `toolCalls`, `buildDurationSeconds`, `usage`, `buildError`, `build`, `buildRounds`, `buildSessionId`, `buildStartedAt`), the reviewer's under `review` (and `reviewStartedAt`), and `role`. Nothing reads them.

### The live feed (#194)

A run's transcript reaches the artefact store only when the run ends, so until #194 a running item showed `building` and nothing more. The live feed is a view of what the invoker already receives; no new path leaves a session, and the run's outcome never depends on it.

- **The channel.** An AppSync Events API, `factorial-live` (orchestration stack), with one namespace, `factorial`: `/factorial/runs/<workItemId>/<stage>/<round>` for each agent run, `/factorial/work-items/<workItemId>` and `/factorial/work-items` for progress. IAM authorises connecting, publishing and subscribing; there is no API key. Only `factorial-invoker` and `factorial-live-forward` hold `appsync:EventPublish`, on the namespace (`factorial-live-publish`); a person subscribes with their own credentials (`docs/finding-a-run.md`, section 6). The runtime boundary allows only `appsync:EventPublish`, on a namespace named `factorial`; the agent boundary denies `appsync:*`.
- **What the invoker publishes.** After it appends an event to the transcript and the log tally, the invoker publishes `{ workItemId, attempt, role, stage, round, seq, at, event }` (`seq` the event's stream number, `at` when it arrived), redacted as the transcript is, with the text of `text` and `reasoning`, a tool call's input and a tool result's content cut to their first 16 KiB (`truncated`, `bytes`), a `harness` event as its name, and any event still over 64 KiB as its type alone. Up to five events per request, sent when a batch is full or 250 ms after the first waits, one request at a time (`packages/invoker/src/live-publisher.ts`). A failed or refused publish counts as dropped, is logged as `live publish failed` at most once a minute, and never fails the run; `usage.json` records `live: { published, dropped, chunks }`. Requests are SigV4-signed (`@factorial/live`, with `@smithy/signature-v4`); no client library. The invoker's public subnets reach the API's public endpoint, with no VPC endpoint.
- **Catch-up chunks.** Every 200 events or 30 seconds, and at the end, the invoker stores the transcript lines since its last chunk (table above), the same redacted, uncut lines, each with its `seq` (every transcript line has carried one since #194). Uploads go one at a time; a failed one is counted (`live chunk not stored`) and its number is not reused. The chunks take only the lines the transcript kept, so its 50 MB cap covers them. A late reader subscribes, reads the chunks, then drops what it already has (`OrderedFeed` in `@factorial/live`). Letting a reader `attach` to the Runtime session was rejected: it would give a second principal a path into a live session.
- **Progress on the ledger row.** The invoker replaces one attribute, `live`, every 60 seconds and on `run.started` and `run.ended`, and once more when it finishes (`ended: true`): the run's role, stage and round, `seq`, events, tool and model calls, usage, cost, elapsed time, last event and the version's limits. Mid-run the cost is the sum of the hosts' per-call estimates (`model.call` `cost`, contracts/run/v1/, added by #194 and sent by the pi host); after `run.ended`, turns and cost are the harness's. The write is conditional on the row existing and replaces the attribute whole, so retries are harmless. Nothing in the pipeline reads it.
- **Work-item progress.** `factorial-live-forward` (`AutoPublishAlias: live`) publishes to both work-item channels: each `WorkItemProgress` event as it is (rule `factorial-live-progress` on `factorial-work`), and the state machine's execution status changes as `{ eventId, workItemId, transition, at }` (rule `factorial-live-execution` on the **default** bus, where AWS sends them, matching only this state machine). The execution's name is EventBridge's (#203), so the id comes from the WorkItem in the execution's input; nothing else of the input, output or error is forwarded. Both are at least once: messages carry `eventId`, and the forwarder drops repeats it has seen while warm. Its role holds the publish policy alone. A notice still failing after two retries, or older than five minutes, is dropped.
- **A terminal reader.** `scripts/tail-run.ts <workItemId> [stage] [round]` connects with the caller's credentials, subscribes, reads the chunks from the bucket and prints the run in order, until it ends.
- **Cost.** At list prices (2026-10-30): $1.00 per million operations, each published or delivered event counted per 5 KB, and $0.08 per million connection-minutes. The largest recent work item is about 1,150 operations with two subscribers, about $0.001.

### Outcomes and the GitHub reporter (#165)

Results leave the pipeline the way requests enter it: as one event, read by a component for the source type. Every terminal state emits an `Outcome` (`contracts/outcome/v1/`), and a reporter per source type tells the requester. The state machine names no GitHub comment operation.

- **Outcomes.** `emitOutcome` (`lib/outcome.ts`) is called by Intake (`refused`, with its reason), Report (`no-changes`, `tests-failed`, `invalid-plan`, `failed`) and OpenPullRequest (`pr-opened`, `pr-updated`). It validates the outcome, writes `outcome/outcome.json`, sets `result` on the ledger row and puts an `Outcome` event (source `factorial.outcome`) on `factorial-work`, in that order. The outcome carries pointers only: the source and `inReplyTo` copied from the WorkItem, the route and thread, the artefact prefix, the pull request, branch, tested commit and saved work. A duplicate emits nothing. The three functions hold `events:PutEvents` for this source alone (`factorial-outcome-events`); Report no longer holds the GitHub App policy.
- **What delivery needs** is in `report.json`, written before the outcome: `delivery` holds facts, not text (the builder's summary as Collect read it, the rework's points and the answers, the test, review and pull request facts, the run details, the saved branch, the plan's problems, the error's name and never its cause, and a refusal's reply when a person asked), so each reporter words them its own way.
- **The GitHub reporter**, `factorial-report-github` (`AutoPublishAlias: live`, `packages/orchestration/src/reporters/github/`), serves every `github-*` source. The rule `factorial-report-github-outcome` routes it every `Outcome` whose `detail.source.type` starts `github-`. It reads that attempt's `report.json` (granted by key: `*/report.json`) and nothing else of the store, then posts one comment where the request came from: the pull request the turn continued (`inReplyTo`), otherwise the source issue, read from its URL. `pr-opened` says on the issue where the pull request is; `pr-updated` replies on the pull request (`reworkComment` in `pr-body.ts`) and re-requests review; the four Report results say what happened (`reporters/github/messages.ts`); `refused` answers only when a reply is due. What the agent said on a no-changes turn is capped at 4,000 characters, headings and tags neutralised, and cannot mention anyone, like every other piece of agent text it posts.
- **Started notice** (#205): the rule `factorial-report-github-progress` routes only a round-1 Build start from a GitHub source to the same function: a `WorkItemProgress` event whose `detail` has `stage` `Build`, `transition` `started`, no `round` and a `source.type` starting `github-`. That is one invocation per work item. The rule is a filter for cost; the reporter repeats the checks. For a `github-issue` item it reacts to the issue with eyes and posts one comment: work has started (with the work item id) and a pull request or a comment will follow. Rework sources get nothing, because Intake already reacts to them. The issue number is read from `https://github.com/<owner>/<name>/issues/<number>`, which must name the event's repository (case aside); one that cannot be read is logged (`issue number not readable`) and ignored. The reaction is best effort. Before commenting, the reporter sets `startedNotifiedAt` on the ledger row with a condition; a failed comment removes the claim so the retry posts it.
- **Delivered once.** Before posting an outcome the reporter claims it on the ledger row (`outcomeDelivery: { claimedAt, deliveredAt?, released? }`) with a write conditional on the row existing and on no confirmed delivery and no live claim; after posting it confirms. A failed attempt releases its claim; a claim older than its two-minute lease (longer than the function's 60-second timeout) can be taken over. An attempt that meets a live claim fails, so Lambda retries it later. Every outcome comment ends with a hidden marker, `<!-- factorial:outcome <workItemId> -->`, and an attempt that takes over a claim first lists the target's comments since the outcome was built (less five minutes for clock skew) and posts nothing if the App's bot user already posted one with the marker. A redelivered event, or a work item with no row, posts nothing.
- **Delivery never fails the turn.** The reporter writes only its own delivery record and the started-notice claim, never the status. EventBridge invokes it asynchronously: after Lambda's retries (`MaximumRetryAttempts: 2`, `MaximumEventAgeInSeconds: 3600`, on the `live` alias), or when EventBridge cannot deliver to it, the event goes to the SQS queue `factorial-report-github-failed` (SQS-encrypted, 14 days; the queue policy lets only the two rules write; a message is the event, metadata only), and the alarm `factorial-report-github-failed` goes into `ALARM` at one visible message. The alarm has no action until #16's alerts topic. Delivery is idempotent, so a message can be put on the bus again once the cause is fixed (`docs/finding-a-run.md`).
- The function's role holds `dynamodb:UpdateItem` on the ledger, `s3:GetObject` on `*/report.json`, the GitHub App policy (tokens with `issues: write`, and `pull_requests: write` for a pull request target or a re-request, scoped to the one repository) and `sqs:SendMessage` on its queue. It puts no event.
- A reporter for another source (Jira for #61) is its own function and a rule on its `source.type`; nothing in the state machine changes. Intake's eyes reaction on an admitted comment turn stays in Intake, which already holds a token for the turn.

### The thread outcome (#204)

Whether a pull request was merged is the only signal of whether the work was accepted, so it is recorded on its thread, the unit that spans the first turn and every rework.

- The rule `factorial-pull-request-closed` on `factorial-work` routes `PullRequestClosed` events to `factorial-thread-outcome` (`AutoPublishAlias: live`). It finds the thread through `pullRequestKey-index` and sets `outcome: { state: merged | closed, at, by, mergeCommit? }` on it, `at` being when it closed. The write is conditional on the thread recording that pull request number from that branch, and on it holding no later close, so a redelivered event sets the same values and an old one delivered late changes nothing. It leaves `version` alone: the outcome is not an admission. A pull request no thread records (opened before #163, or not by Factorial) is logged and ignored.
- It then announces the outcome as a `WorkItemProgress` event for `prOpenedBy` (`stage` `PullRequest`, `transition` `merged` or `closed`, `pullRequest: { number, by, mergeCommit? }`; see The progress record), built from that item's ledger row. Best effort: the thread is the record, and a failed announcement is logged.
- The function's role holds `dynamodb:Query` on `pullRequestKey-index`, `dynamodb:UpdateItem` on the threads table, `dynamodb:GetItem` on the ledger (for the event's source and repository), `factorial-progress-events`, and `sqs:SendMessage` on its failed-event queue. No GitHub access and no artefacts.
- Failures go where the reporter's do, to their own queue: after Lambda's retries (`MaximumRetryAttempts: 2`, `MaximumEventAgeInSeconds: 3600`, on the `live` alias), or when EventBridge cannot deliver, the event goes to `factorial-thread-outcome-failed` (SQS-encrypted, 14 days). A message is the `PullRequestClosed` event and can be put on the bus again once the cause is fixed.
- Gaps: a reopened pull request keeps its outcome until it closes again, when the latest close replaces it; reopening is not recorded. Pull requests closed before #204 deployed, or before the App subscribed to **Pull request** events (`docs/github-app.md`), have no outcome.

### The command centre (#57)

A local operations console, `packages/dashboard`: a Next.js app a reviewer starts with `npm run dashboard` and their own AWS credentials. It deploys nothing, and no role Factorial owns reads anything new; `docs/dashboard.md` is the full description.

- **Access.** It binds to `127.0.0.1` only, refuses any other `Host` (403) and anything without the cookie a printed one-time token is exchanged for (401). Pages carry a CSP with nonces and `frame-ancestors 'none'`. It reads with the policy in `docs/dashboard.md`: the ledger and threads tables, the artefact bucket, the two stacks, the Runtimes' `live` endpoints, CloudWatch alarms and metrics, and `appsync:EventConnect` and `EventSubscribe` on `factorial-live`.
- **Data.** Server-only modules, one per source, behind read-only JSON routes (`/api/work-items`, `/api/work-items/{id}`, its artefacts, `/api/running`, `/api/status`). Lists scan the ledger, cached for 5 seconds; a finished item's artefacts and every chunk stay in memory for the process's life. A turn is running until its row has a `result`; rows from before #165 never got one and count as ended.
- **The live stream.** One server-sent events stream per tab (`/api/live`), its channels changed without reconnecting; one upstream subscription per channel however many tabs want it. A run channel is sent from `seq` 1, merged from the catch-up chunks and the channel with `OrderedFeed`, each event once and in order, until `run.ended`; reconnects use backoff and re-read the chunks.
- **Views.** The shell (rail, status bar with the live version, each Runtime's `live` version, the stream's state, the bus rate and the alarm count), the shared components, the Work items view (filters, source filter, search, ticking durations, cost and review per turn) and each item's detail. Overview and Run & transcript are #58; Metrics & cost and Health #59, each shown as not set up until then.
- Everything a model, tool or requester wrote is rendered as text with control and bidirectional characters removed; only links the app builds itself are clickable; artefacts are served as JSON or plain text with `nosniff` and a sandbox CSP.

## Logging and correlation

Every orchestrator Lambda and the invoker log one JSON object per line through `@factorial/log` (`workItemId`, `attempt`, `stage`, `level`, `message`, redacted). The work item id is the agent session id, the ledger key, the artefact prefix and the `workItemId` attribute on every log line and state output. EventBridge starts the execution and names it, so the execution name is not the id; Intake records the execution's ARN on the ledger row as `executionArn` (#203). AgentCore traces are not yet exported (CloudWatch Transaction Search is off), so finding a run's trace by its id is still unproven.

## Stacks and deployment

- `factorial-foundation` (deployed by a human, `docs/bootstrap.md`): GitHub OIDC provider, deploy role, CloudFormation execution role, the two permissions boundaries, the artefact bucket and the agent environment ECR repository. The deploy role ARN is the `AWS_DEPLOY_ROLE_ARN` repository secret.
- The deploy workflow runs after CI on `main`, deploys the stacks listed in `deploy.yml`, in that order (every template but `foundation.yml`), and then promotes the runtime `live` endpoints. It skips itself when nothing functional changed since the last deploy (`scripts/classify-changes.ts`).
