# How Factorial works today

The record of what is deployed and how it behaves, stage by stage. `CLAUDE.md` holds what is agreed and binding (requirements, target architecture, what is fixed from day one, the shape of the current stage and the conventions); this document holds the detail behind its **Current stage** section. When a change completes or alters a stage, both are updated in the same pull request.

Stage 0 is complete: on 2026-10-17 a labelled issue (#2) became a tested pull request (#3) with no human step in between. `docs/finding-a-run.md` goes from a work item id to everything a run produced.

## Triggers

- The triggers stack (`factorial-triggers`) holds the `factorial-work` event bus, the webhook secret and the GitHub issue adapter (`packages/triggers-github-issues`) behind a function URL on its `live` alias.
- Factorial acts as a GitHub App (`docs/github-app.md`), created and installed by a human. Adding the `factorial` label to an issue produces a `WorkItem` on the bus; the person who added the label is the requester.
- The `WorkItem` contract (`v1`) is in `contracts/workitem/v1/` (JSON Schema, with the event envelope and change process in `contracts/workitem/README.md`), validated by `@factorial/workitem`. It carries optional lineage: `group` (`id`, `size`, `index`: the items one trigger produced) and `parentId` (the item whose Plan stage emitted it). Prepare copies them onto the ledger row as `groupId`, `groupSize`, `groupIndex` and `parentId`, and `groupId-createdAt-index` and `parentId-createdAt-index` list a group's or a parent's items. Nothing produces or reads them yet.

## The state machine

The orchestration stack (`factorial-orchestration`) holds the `factorial-work` state machine (Prepare → Build → Collect → Test → PrepareReview → Review → CollectReview → OpenPullRequest, with Build → SaveWork → ContinueBuild → Build when the builder runs out of steps) behind its `live` alias, the bus rule that starts it, the `factorial-work-items` ledger, the Fargate invoker (`packages/invoker`), the orchestrator Lambdas (`packages/orchestration`) and the artefact store. Every state's output carries `workItemId` and `attempt`.

### Prepare

- Creates the ledger row and the artefact prefix, clones the repository into the builder's session on a new `factorial/<workItemId>` branch, hands `/workspace` to the `agent` user, and seeds `/workspace/notes.md` with the request under `# Task` (the harness drops nothing from the conversation at this model, but the notes file is what a later session starts from).
- **Resume:** a new item from the same source as an earlier attempt that failed after saving work, or whose tests failed, resumes on that attempt's `factorial/*` branch. Prepare finds it through the ledger's `sourceKey-createdAt-index` and adds a "Previous attempt" section to the notes; the builder's first message also says the attempt resumes and to build on the branch's commits. A resumed item's attempt is one more than the attempt it resumes, and its artefact prefix uses its own id. Attempts made before the index existed are not found.
- **Rework** (`context.kind: "rework"` in the `WorkItem` contract): Prepare checks out the previous item's `factorial/*` branch instead of creating one, and writes `/workspace/rework.md` with the review details and, for failed checks, the failing jobs' logs (last 200 lines, redacted, fetched with a short-lived `actions: read` token outside the sandbox). The agent is told to address each point on the existing branch and to say in `summary.md` how each was handled. The ledger links the rework item to `previousWorkItemId` and the PR number. No trigger produces rework items yet.

### Build

- **Planning** (since 2026-10-25, `docs/agent-sdk-plan.md` phase 3.1; a separate planner harness and the Plan and CollectPlan states before). The builder first runs its `plan` subagent (Read, Grep, Glob, web search, and Write for the two plan files only, enforced by the `PreToolUse` hook; 40 turns; the builder's model), whose prompt is ported from the planner harness's. The subagent writes `/workspace/plan.json`, the plan the builder follows (steps in order by `id`, each with files and a verification; tests to run and add; risks; open questions; optional `followUp` for work that belongs in a separate item; contract `contracts/plan/v1/`, validated by `@factorial/plan`), and `/workspace/plan.md`, its explanation for humans. A `PostToolUse` hook in the host validates `plan.json` after each `Write` or `Edit` to it and sends the errors back to whoever wrote it, normally the subagent; after the second invalid plan every further tool call is denied and the run ends. The `Stop` hook will not let a run end without a valid plan. These spare a wasted build; Collect is the gate.
- The builder (`factorial_builder`, an AgentCore Runtime with role `factorial-agent-builder`; see Agents) follows `plan.json` step by step, commits after each coherent step, keeps running notes in `/workspace/notes.md`, and writes `/workspace/summary.md` with a `## Plan steps` section reporting each step by its `id`. Its prompt sets an exploration budget before the first edit, forbids installs for documentation-only changes, states once that GitHub belongs to the orchestrator, and keeps the builder to executing the request.
- When a round starts with a plan (a later round), the host appends `plan.json`'s steps (id, description, files, verification) to the builder's first message, so following the plan does not depend on the model opening the file.
- If the builder's `summary.md` lacks a `## Plan steps` line for any step id in `plan.json`, the host's `Stop` hook sends it back to write them, at most twice.
- The Fargate invoker runs each agent to completion and Step Functions waits on it (`ecs:runTask.sync`). It takes the role and where it runs from the state machine's container overrides, records `role` on the ledger row, and passes the ids in the `baggage` header. For the builder (`TARGET=runtime`) it calls `InvokeAgentRuntime` on the `live` endpoint with a `run` request and reads the host's SSE stream; if the stream ends without a result it re-attaches from the last message number it holds, and the host's `status` gives the final outcome. For the reviewer it invokes its harness and passes no `maxIterations` or `timeoutSeconds` (each harness version's own limits apply).
- A builder that stops at a turn, budget or time limit (`error_max_turns`, `error_max_budget_usd`, `max_duration`) is incomplete: the invoker records `buildError` and exits with code 3, so a half-finished change is never tested or opened as a pull request. `success` is complete; any other stop is an error.
- Session commands on the Runtime run as root through the command API, so the orchestrator hands `/workspace` to the `agent` user after its last seeding write, and every command after the model has run (Collect's inspection, leftover commit, bundle and file export) drops to `agent` with the host's own restrictions (`setpriv`, no new privileges, empty bounding set).
- **Rounds.** A builder session has turn, budget and time limits, so a plan can outlast it. When the builder is incomplete, SaveWork pushes its work and, instead of reporting failure, ContinueBuild seeds a fresh builder session (`<workItemId>-r<round>` on the same Runtime) at the branch head (or the start commit when the round committed nothing) with the plan read back from the artefact store and validated again (none when the previous round ended without a valid plan, and the section then says to plan first), the previous round's `notes.md` (stored by Collect before the push) and a "Continuing (round N)" section: what is on the branch, the `git log` and `git diff --stat` to run, check each plan step against the commits, carry on from the first step not done. The builder runs again with `BUILD_ROUND` set, and its prompt says to read that section first. Rounds repeat until the builder finishes or `MaxBuildRounds` (3, a template mapping; 6 before the spike) is reached, when the item is reported incomplete ("in N sessions") with the saved branch. The branch and `notes.md` are the memory between rounds; nothing is read out of the old session. There is no limit on a work item's size beyond that.

### Collect and SaveWork

- Collect first reads the builder's plan: only `/workspace/plan.json` and `/workspace/plan.md`, as the `agent` user, at most 64 KiB each, redacted; it validates the JSON, stores both with `plan/validation.json`, and records the plan's size (`planSize`: steps, distinct files, description characters, follow-up items) and `planSteps` on the ledger row beside the builder's usage. A build that ends without a valid plan pushes nothing and ends with `invalid-plan` (`planErrors` on the row), reported on the issue. SaveWork stores the plan whatever its state and saves the work regardless. There is no limit on a plan's size beyond the contract's 30 steps.
- Collect inspects the builder's session (hostile once the agent has run), commits anything left uncommitted, stores the session's files, and bundles the new commits. The push happens from a pristine clone in a separate clean-room session with hooks disabled and the token sent as a header; every commit is re-created with the App's identity, and the push is always a fast-forward on top of the head the session started from, never a force push.
- When the build stops (a model or API error, the invoker task stopping, or the builder running out), SaveWork runs Collect in salvage mode with the Build failure and the round's session id: whatever the agent committed, plus any uncommitted changes in a commit marked as saved work in progress, is pushed to the work branch, and Collect reports `incomplete` when the stop was the builder's own limit. An incomplete build continues in another round (see Build); any other failure, or the last round, is reported: no tests run and no pull request is opened, the failure comment links the branch, and relabelling the issue resumes from it.

### Test

- The test workflow (`test.yml`) is dispatched on the default branch, so its definition is always the trusted one. The work commit is checked out as data in a job without credentials; a separate job reports the result through a Step Functions task token, assuming the test callback role (its ARN is the `AWS_TEST_CALLBACK_ROLE_ARN` repository secret). A failed run ends the item as `tests-failed`, reported on the issue with the branch left for inspection.

### PrepareReview, Review and CollectReview

- PrepareReview clones the pushed branch into a fresh reviewer session, checks that its head is the tested commit, and writes the validated `plan.json` and `plan.md` (read back from the artefact store), the builder's `summary.md` and `diff.patch` (three-dot against the base branch). It also computes the pull request's facts in that session, before any agent runs there: contract and test-file paths, dependency changes (every changed `package.json`, licences as the root lockfile at the pushed head states them, which the body labels as the lockfile's claim) and deploy impact from the base branch's `.factorial/pr-body.json` (`deploy.paths` and `deploy.humanSteps`, each `{prefix, note}`; absent or invalid means "not determined"). They travel in the state as `prFacts`, capped at about 6 KB.
- Before the reviewer runs it works out which changed files are sensitive: built-in rules that hold for any repository on GitHub (Actions workflows and composite actions, `CODEOWNERS`, any `.gitattributes`, `.factorial/`) plus the target repository's own rules in `.factorial/sensitive-paths.json` (exact paths, prefixes, file names and diff content patterns, each with a reason; contract in `contracts/review/v1/sensitive-paths.schema.json`). The rules file is read from the base branch, never the branch under review, so a change cannot loosen the rules that judge it; an invalid file is logged and stored as `rulesProblems`, and the built-in rules still apply. Rename detection is off and diffs are forced to text without textconv, so a moved file is caught under its old path and a branch's `.gitattributes` cannot hide lines. Factorial's own rules (the foundation template, permissions boundaries, the workflow and change-classification checks) live in its `.factorial/sensitive-paths.json`, not in the code.
- The reviewer (`factorial_reviewer`, role `factorial-agent-reviewer`) judges the change against the request and the plan, treating everything it reads as untrusted, with the flagged files and their reasons in its prompt, and writes `/workspace/review.json` (verdict, four scores from 1 to 5, findings, summary; contract in `contracts/review/v1/`, validated by `@factorial/review`). Its prompt budgets 25 reads and has it write the review early and refine it.
- CollectReview reads only `review.json` out of the session (at most 64 KiB, redacted), validates it and adds a high-severity finding for every sensitive change, whatever the reviewer wrote about it. The review is advisory: the PR body shows the verdict, scores and findings, and if any review step fails the PR still opens, saying the review did not complete. The ledger holds the reviewer's run under `review` and the result as `reviewVerdict`, `reviewScores` and `reviewFindings`.

### OpenPullRequest and Report

- OpenPullRequest verifies the branch head is the tested commit and opens the pull request, whose body `pr-body.ts` builds as seven fixed sections: Summary, Impact, Review focus, Automated review, Tests, Plan (departures only, read from the builder's `- <id>: done|skipped|changed: <why>` lines; the full list, with descriptions read back from `plan/plan.json`, is collapsed) and Run details (collapsed table with the artefact prefix). Facts come from `prFacts`, the test result, the plan and the review; the builder's `summary.md` sections fill only their own slots, redacted, capped and with a placeholder when missing. Values the branch controls (paths, package names, versions, licences) appear only as code spans, so they cannot add Markdown or close the collapsed blocks. Rework results use the same body. Every terminal path writes `report.json`, and Report comments on the issue when no pull request follows (no changes, tests failed, invalid plan, or a failure, with the saved branch linked).

## Agents

- **Builder** (`factorial_builder`, since 2026-10-25; `docs/agent-sdk-plan.md` phase 2, results in `docs/harness-vs-runtime.md`, **Spike results**). An AgentCore Runtime from the `agent-runtime/` image (Node 22, git, gh, jq, `quiet`, python3, and cfn-lint at CI's version) running Factorial's host process (`packages/agent-runtime/`) around the Claude Agent SDK's `query()`. The host runs as root and starts Claude Code as the `agent` user through `claude-as-agent`, so the model cannot signal or reconfigure it; the run's transcript and result are kept in root-only `/var/lib/factorial`.
- The models are fixed on the Runtime version and named by purpose: Claude Sonnet 5.5 for the main loop, Haiku 5.5 for the read-only `explore` subagent (30 turns) and the SDK's background calls; the `plan` subagent inherits Sonnet, all through the EU inference profiles on Bedrock. The execution role may call only those profiles; there is no model key. Limits, also on the version: 150 turns, $5 and 6,600 seconds (below `BuildTimeoutSeconds`), set from the spike.
- A `PreToolUse` hook denies file edits outside `/workspace` or under `/workspace/.claude` (the SDK's own files) and `git push`, `gh auth` and `gh api`; it constrains a prompt injection and is not the access gate. Compaction is the SDK's, as the context nears the model's 1M-token window; no run has reached it yet (the largest peaked at 112k). Web search is the host's in-process `web_search` tool, which signs calls to the `factorial-web-search` gateway with the execution role. `usage.json` records the Runtime version serving `live`, the models, the limits and the SDK's cost at list price.
- **Reviewer.** A harness on the `agent-environment/` image (Node 22, git, gh, jq, and `quiet`, which keeps command output in `/workspace/logs` and prints a short report); the planner was one too until phase 3.1. The image and the session hold no credentials. The model is GLM 5.3 Flash through the Z.ai API, via an AgentCore Identity credential provider and the harness's LiteLLM model configuration. Model id, reasoning effort, loop timeout, iteration cap and output cap are template constants per role. LiteLLM has been in use since 2026-10-17 (#17): the OpenAI chat-completions configuration hit Z.ai 1214 rejections mid-run.

| Role | Effort | Iterations | Loop | Web search |
|---|---|---|---|---|
| Reviewer | high | 40 | 15 min | no |

- The reviewer harness is configured with summarisation truncation, but the harness applies truncation only when the conversation exceeds the model's context window, which GLM 5.3 Flash's 1M-token window has never reached.
- The deploy workflow tags each image with a hash of its inputs, builds it only when that hash is new, and passes the tags to the agent stack.
- The template is laid out one block per role (see **Agent roles** in `CLAUDE.md` Conventions). The deploy workflow's final step moves every harness's and runtime's `live` endpoint to its newest version.

## The artefact store and the ledger

The artefact store (`factorial-work-artefacts-<account>`, in the orchestration stack) keeps each run's record under `<workItemId>/<attempt>/`. The ledger row holds `attempt` and `artefactPrefix`, and the pull request body links the prefix. The store is write-only, with two read exceptions by the orchestrator: the plan files (PrepareReview and ContinueBuild) and the previous round's `build/notes.md` (ContinueBuild).

| Key | Written by | Contents |
|---|---|---|
| `workitem.json`, `prepare/branch.json` | Prepare | The work item and the branch |
| `plan/plan.md`, `plan/plan.json`, `plan/validation.json` | Collect (SaveWork too; the latest round's) | The builder's plan, valid or not, and its validation; the plan subagent's run is in the build transcript (`plan/transcript.jsonl` and `plan/usage.json` are the planner harness's, before phase 3.1) |
| `build/transcript.jsonl`, `build/usage.json` (round 1), `build/round-<n>/transcript.jsonl`, `build/round-<n>/usage.json` (later rounds) | Invoker | Every harness stream event or SDK message (redacted, capped at 50 MB with a truncation marker) and the usage: summed and per-call tokens, harness version, model id, stop reason, tool calls, duration; written on every exit including a stopped task (`stopReason: "interrupted"`) |
| `build/round-<n>/continuing.json` | ContinueBuild | The round's session id and the commit it started from |
| `build/summary.md`, `build/notes.md`, `build/rework.md`, `build/logs/<name>`, `build/logs/index.json`, `build/bundle.git` | Collect, before the push (SaveWork too; the latest round's) | The session's files; command logs 5 MB per file keeping the end and 50 MB in total, with the index listing what was stored, truncated or skipped |
| `test/result.json` | OpenPullRequest, or Report when tests fail | The test outcome and run |
| `review/prepared.json` | PrepareReview | The tested head, changed paths, the rules applied and the sensitive paths |
| `review/transcript.jsonl`, `review/usage.json` | Invoker | The reviewer's run |
| `review/review.json`, or `review/error.json` and `review/review.raw.json` | CollectReview | The review with the orchestrator's findings added, or why there is none |
| `pr/pr.json` | OpenPullRequest | The pull request |
| `report.json` | Every terminal path | The outcome and a short reason |

The ledger row points at the build records with `build.transcriptKey` and `build.usageKey` (the latest round's), holds `buildRounds`, `buildSessionId` (the latest round's session) and `buildUsageTotal` (usage summed over rounds; `usage` is the latest round's), and keeps the existing `usage` totals until the progress record (#15) defines per-stage fields. Token usage is recorded the way Z.ai reports it: `inputTokens` is the gross prompt size including cache reads, and `uncachedInputTokens` is what is billed at full rate.

## Logging and correlation

Every orchestrator Lambda and the invoker log one JSON object per line through `@factorial/log` (`workItemId`, `attempt`, `stage`, `level`, `message`, redacted). The work item id is the execution name, the agent session id, the ledger key, the artefact prefix and the `workItemId` attribute on every log line and state output. AgentCore traces are not yet exported (CloudWatch Transaction Search is off), so finding a run's trace by its id is still unproven.

## Stacks and deployment

- `factorial-foundation` (deployed by a human, `docs/bootstrap.md`): GitHub OIDC provider, deploy role, CloudFormation execution role, the two permissions boundaries, the artefact bucket and the agent environment ECR repository. The deploy role ARN is the `AWS_DEPLOY_ROLE_ARN` repository secret.
- The deploy workflow runs after CI on `main`, deploys every numbered template above `00`, and then promotes the harness and runtime `live` endpoints. It skips itself when nothing functional changed since the last deploy (`scripts/classify-changes.ts`).
