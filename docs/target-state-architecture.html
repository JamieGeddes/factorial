Where the triager sits, and what it is allowed to decide

QuestionAnswerWhy
WhereInside Intake, the first state of the execution, replacing decideRoute for free-text requests. Not in the adapter and not a separate service in front of the bus.The adapter is public-facing, credential-free and must answer in seconds. Intake already has the ledger row, the thread, a read token and the record, so a triaged request is correlated like any turn.
What it readsThe request, who asked, the thread’s previous turns and their outcomes, the target registry (which repositories Factorial may work on, from configuration), and each target’s triage hints from its .factorial/. Intake fetches all of it; the triager has no tools.A classifier with no tools can be tested on a fixed set of requests and cannot be steered by the text into reading anything else.
What it returnstriage.json under contracts/triage/v1/: a verdict from the route enum (change, answer, propose, ignore), a priority from an enum with a reason, and one or more items, each a repository, a title and the request rewritten for that repository.The orchestrator validates it and acts on nothing outside the schema; an invalid verdict becomes an ask-back, not a build.
What it cannot decideIntegrate (a fact about the pull request), admission (eligibility, one in flight, the rework limit), the cap on fan-out, whether a pull request opens, and anything about deployment.Policies run after the model in deterministic code, so a crafted request can at worst pick the wrong route or priority for its own turn.
One or more itemsOne item: the turn continues on its route. Several: Intake puts one derived WorkItem per item on the bus with group and parentId, each with its own execution, ledger row and thread; derived items take the parent’s route and are not triaged again. Above a cap, or when the request named no repository, the list is posted as a proposal and approval is the next turn.This is the fan-out the contract README reserves for Intake, and the proposal reuses #169 rather than adding a human wait inside an execution.
PriorityRecorded, not acted on, until a concurrency gate exists: ledger, intake.json and the Outcome carry it, so reporters and the dashboard show it. The gate releases queued turns by priority then age under an account-wide cap.The contract README leaves priority out of the WorkItem on purpose: it is a decision, and today nothing schedules.

What stays fixed

  • One bus, one WorkItem in, one Outcome out. Adding a source is an adapter and a reporter.
  • A deterministic graph with agents inside states. Routes are a Choice over an enum the orchestrator validated; no agent picks the next stage.
  • Credentials stay in orchestrator Lambdas; sessions are hostile once a model has run; commits leave as a bundle and are pushed from a clean room; agents never deploy or promote Factorial. Verification is Factorial's gate and runs in its own sessions; the target's CI on the pull request is the independent second check.
  • Every turn writes under <workItemId>/<attempt>/; the ledger holds pointers, never content; the work item id correlates everything, and the thread key joins the turns on one branch.
  • Roles are immutable Runtime versions behind live endpoints; the manifest's copy in the host is the one that counts.
