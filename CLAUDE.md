# Factorial

Factorial is a software factory: an agentic AI system that builds and refines software codebases, built on AWS AgentCore and associated AWS services. It builds itself incrementally.

This file is what is agreed and binding. **Requirements** and **Target architecture** are where Factorial is heading, not yet implemented. **Fixed from day one** must never be weakened. **Current stage** is what exists and what to build next: work to it, and implement target features only when the task asks. **Conventions** apply to every change.

Also binding: `docs/architecture-principles.md`. `docs/security.md` is the threat model. `docs/current-stage.md` is the detailed record of how the deployed system behaves. `docs/design-conversation.md`, `docs/design-plan.md` and `docs/design-extension-points.md` are background and proposals, not agreed.

## Requirements

- **Inputs:** Jira tickets, GitHub issues and production alerts, with new trigger types addable without changing the core.
- **Output:** a pull request for human approval, raised only once the change is implemented on a branch, has passed existing and new automated tests, and has passed a smoke test in an ephemeral sandbox AWS account.
- **Extensibility:** new trigger types, new context providers (e.g. knowledge graphs), integrations with external systems.
- **Self-bootstrapping:** Factorial builds itself from a minimal first version; new requirements arrive as work items; the end goal is building and maintaining other software (e.g. bulk Lambda runtime upgrades across repositories). Every PR against its own codebase is approved by a human, and each successful deploy becomes the version used for the next action.

## Target architecture

- **Triggers: EventBridge.** One bus. Each trigger source is a thin adapter Lambda that emits a canonical `WorkItem` event; adding a trigger adds an adapter and nothing downstream changes. Adapters normalise and never interpret: they record what happened and what it continues. Intake, the first state, resolves the work item's thread (one per branch) and chooses its route from a fixed enum in one pure function; a triage agent that reads a comment to tell a change request from a question or noise replaces that function and nothing else.
- **Orchestration: Step Functions.** A fixed stage graph (intake → plan → build → verify → smoke → PR), deterministic, with agents inside the states. It never deploys Factorial. Verification runs in sessions Factorial owns, from the verifiers the target declares in its `.factorial/`, never by dispatching the target's CI. Results leave as inputs arrive: every terminal state emits one `Outcome` event, and a reporter per source type tells the requester, so the state machine knows no source system.
- **Agents: pi on AgentCore Runtime.** Each role is a Runtime whose container runs Factorial's host process around pi (`@earendil-works/pi-coding-agent`, MIT): the agent loop, the role's policy and its limits run in the root host, and every tool that runs a command or touches a file runs as the unprivileged `agent` user. The role's definition (model, prompt, tools, subagents, policy, limits, image) is fixed in an immutable Runtime version; nothing overrides it at invoke time, and the request carries only the prompt. The model is Claude on Bedrock, reached with the role's execution role, which names the inference profiles it may call. Deterministic steps (clone, test, push) use the session command API, on the same endpoint qualifier as the invocation. The sandbox holds no credentials; orchestrator Lambdas mint repository-scoped GitHub App tokens and do all GitHub access. A session is hostile once its agent has run: commits leave it as a git bundle and are pushed from a pristine clean-room clone with hooks disabled. Each verifier runs at the tested commit in a fresh session on a verifier Runtime whose role can call no model and read nothing of Factorial's, cloned by the orchestrator with a token that never enters the session; the PR step verifies the branch head is the commit every required verifier passed. A build that stops early still has its committed and uncommitted work saved to the branch, and no unfinished or untested change becomes a PR. A Fargate invoker runs each invocation to completion (`ecs:runTask.sync`); nothing inside a session is a control signal for the orchestrator, since the model's shell shares the session and its role.
- **Versioning: `live` aliases.** Runtime endpoints, the state machine alias and Lambda aliases are all named `live`; everything references alias ARNs, in-flight executions finish on their version, and moving the aliases is the last step of a successful deploy.

## Fixed from day one

- **`live` aliases** on all three parts, every reference by alias ARN.
- **The `WorkItem` contract** is Factorial's API. Changing it is a deliberate, human-approved decision, never a side effect.
- **Human approval** of every PR against Factorial's own codebase.
- **Agents never deploy or promote Factorial.** Only the GitHub Actions deploy role may deploy or move a `live` alias, enforced by `factorial-permissions-boundary` (runtime roles) and `factorial-agent-permissions-boundary` (agent roles); every role Factorial creates carries one.

## Current stage

**Stage 0: complete** (2026-10-17: labelled issue #2 became tested PR #3 with no human step). Detail in `docs/current-stage.md`.

- **Pipeline:** issue labelled `factorial`, or on a Factorial pull request a "Request changes" review, an `@<slug>` comment or a failed workflow run (rework) → `WorkItem` on the `factorial-work` bus → state machine Intake → Prepare → Build → Collect → Test → PrepareReview → Review → CollectReview → OpenPullRequest. Intake (#163) resolves the item's thread in `factorial-threads` (one row per branch: its pull request and whether it was merged or closed, the turn in flight, the automatic rework count), applies the admission policies there and chooses the route (`change` or `refuse`, `contracts/intake/v1/`). Every stage writes to the artefact store under `<workItemId>/<attempt>/`; the `factorial-work-items` ledger row tracks status and pointers, and under `stages` each stage's start, end and outcome and each agent run's usage, every transition also put on the bus as a `WorkItemProgress` event (`contracts/progress/v1/`, #15) by the orchestrator alone.
- **Outcomes and reporters** (#165): Intake (a refusal), Report and OpenPullRequest end every turn with one `Outcome` (`contracts/outcome/v1/`, pointers only) through `lib/outcome.ts`: `outcome/outcome.json`, `result` on the ledger row, then the event on the bus; `report.json` carries the facts delivery needs. `factorial-report-github` (`packages/orchestration/src/reporters/github/`), selected by rules on `source.type`, posts every GitHub comment, reply and review re-request, once per outcome (a claim on the ledger row and a marker in the comment), and the "started" notice when Build starts in round 1 on a labelled issue; a failed delivery never changes the turn and lands on its queue with an alarm (`docs/current-stage.md`).
- **Agents:** the builder and the reviewer are AgentCore Runtimes running Factorial's host around pi, Claude Sonnet 5.5 on Bedrock (`docs/pi-plan.md`, decided 2026-10-29 after spike #181; on the Claude Agent SDK from 2026-10-25 under `docs/agent-sdk-plan.md`, tag `stage-1-agent-sdk` after the Harness was removed, and tag `stage-1-claude-sdk-final` before the SDK was). Builder `factorial_builder` plans with its read-only `plan` subagent and writes `plan.json` (`contracts/plan/v1/`) and `plan.md`, then follows `plan.json`, commits as it goes, and writes `summary.md`; reviewer `factorial_reviewer` writes `review.json` (`contracts/review/v1/`), advisory only. The host streams each run to the invoker as run events (`contracts/run/v1/`); only its adapter (`src/pi/events.ts`) reads pi's events, so the harness or the model's provider can change on the Runtime alone.
- **Stacks:** `factorial-foundation` (human-deployed: OIDC, deploy and execution roles, boundaries, buckets, ECR), then `factorial-triggers`, `factorial-agent`, `factorial-orchestration`, deployed from `main` by GitHub Actions, which then promotes the Runtime `live` endpoints.
- **Pull request body:** seven fixed sections built only by `pr-body.ts`; facts (paths, dependencies, deploy impact, tests, plan, review) come from the orchestrator, and the builder's `summary.md` fills only its own capped slots (`docs/current-stage.md`).
- **Rules the stages keep:** only named files leave an agent session, capped, redacted and validated; the artefact store is write-only except for the orchestrator reading back the plan files and the builder's notes, and the reporter reading `report.json`; Collect validates the builder's plan, and a build without a valid one pushes nothing and ends `invalid-plan`; a builder that runs out of steps or time continues in a fresh session from the branch and its notes, up to `MaxBuildRounds`; any other early stop saves the work and opens no PR, and relabelling resumes from the saved branch; the reviewer's sensitive-path rules come from the target's base branch (`.factorial/sensitive-paths.json`), never the branch under review.

### Scope and gaps

Triggers: GitHub issues, and events on Factorial's own pull requests for rework. Verification: GitHub Actions tests; no sandbox smoke test, so the output requirement is not met. No staging canary. Only the Runtime `live` endpoints are promoted as a separate step; Lambda and state machine aliases move during the deploy. A change to `.github/workflows/` is pushed with `workflows: write` and CI runs it with the repository's secrets, which are role ARNs only with OIDC trusts bound to `main`: keep it that way and review workflow changes with care. The App token can push to any unprotected branch; `main` is ruleset-protected (`docs/github-app.md`) and the orchestrator pushes only to `factorial/*`. Rework replies on its pull request with an answer per point and re-requests review instead of opening a new one; Intake admits rework only on pull requests whose thread records Factorial opening them, one turn per thread at a time, and at most two automatic reworks after failed checks in a row. The merge-conflict command waits for #155. Its commits reach the pull request's branch before Test, so a failed rework leaves the pull request failing. The test stage assumes Factorial's own test workflow and callback trust (#91, replaced by #167), and the image carries only a Node toolchain, so only Factorial can be a target today; the builder prompt names no repository's paths or commands.

## Conventions

- **Deployments** run through GitHub Actions, except `templates/foundation.yml`, deployed by a human (`docs/bootstrap.md`). Every job that assumes the deploy role declares `environment: production` and the deploy trust gate. The deploy skips when nothing functional changed (**Non-functional paths**).
- **IAM:** every role is named `factorial-*` and carries a boundary: `factorial-agent` or `factorial-agent-*` with `Factorial-AgentPermissionsBoundaryArn`, all others `Factorial-PermissionsBoundaryArn`; only agent roles are passed to AgentCore. AgentCore resources are `factorial_*`; every other resource `factorial-*` (`factorial/` for ECR, Secrets Manager, SSM). The CloudFormation execution role is scoped to those names.
- **Sandbox access:** inner-loop agents may deploy to the sandbox and read its state to verify their work.
- **Infrastructure:** CloudFormation YAML, `.yml` extension, one template per stack, named for it (`templates/<name>.yml` is stack `factorial-<name>`), deployed in the order listed in `deploy.yml` (`foundation.yml` by a human, the rest by the workflow). Lambda templates use the `AWS::Serverless-2016-10-31` transform with `AutoPublishAlias: live`; code is bundled with esbuild from `packages/`, every dependency included (the AWS SDK too: never leave a package for the Lambda runtime to provide, since AWS updates it outside Factorial's deploys), and packaged by `aws cloudformation package`.
- **Triggers:** adding the `factorial` label to a GitHub issue creates a `WorkItem`; the labeller is the requester. On a pull request Factorial opened, a "Request changes" review or a comment starting `@<slug>` from a trusted user, or a failed workflow run on its head, creates a rework `WorkItem`; the mention is the one way to address the App. Its closing, merged or not, is a `PullRequestClosed` event recorded on its thread, never a `WorkItem`.
- **Agent environment:** one custom `linux/arm64` image, `agent-runtime/`, holding no credentials, tagged by a hash of its inputs and rebuilt only when that changes. Every role's Runtime runs it: Node 22, git, gh, jq, ripgrep (as `rg`, a wrapper that runs it as the agent user when root calls it), python3, cfn-lint, `quiet` from `packages/agent-tools` (which keeps command output in `/workspace/logs`), and the host process, which runs the model's tools as the unprivileged `agent` user.
- **GitHub identity:** Factorial is a GitHub App (`docs/github-app.md`). Only orchestrator Lambdas mint installation tokens (`packages/github-app`), scoped to one repository and the step's permissions; the token never enters a session. Commits are re-created under the App's bot user (`<slug>[bot]`) in the clean-room push. App and installation IDs are in SSM under `/factorial/github/`.
- **Promotion:** the deploy workflow's last step moves every Runtime's `live` endpoint to its newest READY version, found from the agent stack's `*RuntimeId` outputs. Templates create endpoints and aliases but never set their target.
- **Agent roles:** one Runtime block per role in `templates/agent.yml` (execution role, runtime, `live` endpoint, outputs `<Role>RuntimeArn`, `<Role>RuntimeId`, `<Role>RuntimeLiveEndpointArn`), with `FACTORIAL_ROLE` selecting the role's definition: its manifest in `@factorial/roles` (stage, statuses, models, first message, shared by the host, the invoker and the orchestrator) and its host part in `packages/agent-runtime/src/roles.ts` (prompt, tools, subagents and policy, defined in harness-neutral terms; `src/pi/` maps them onto pi), with no role conditionals elsewhere; shared parts (`factorial-agent-runtime` policy, web search gateway) outside the blocks. Runtime `factorial_<role>`, role `factorial-agent-<role>`. The invoker serves every role from one task definition, taking `ROLE` and the Runtime from the state machine. Each prompt stays within its role: the builder executes, it does not review or propose architecture.
- **Target repositories:** nothing in the code assumes the target is Factorial. Per-repository settings live in the target's `.factorial/`, read from its base branch; Factorial keeps its own there like any other target.
- **Secrets:** no agent holds a model key: each Runtime role reaches Bedrock with its execution role, which names the models it may call. The GitHub App private key is created by a human and referenced by name. None appear in the repository, templates, parameters or logs.
- **Language:** TypeScript for all code Factorial owns, including the agent host process. The agent loop is pi's, in the host process; each role's definition (prompt, tools, subagents, policy, limits, model) is code versioned by the Runtime version.
- **Compute:** serverless first; Fargate where a container is unavoidable, never EC2.
- **Security:** least privilege per role, no shared credentials, agent roles that can never deploy or promote Factorial.
- **Region:** `eu-west-1`.
- **Layout:** `contracts/` (JSON Schema contracts), `packages/` (TypeScript workspaces), `templates/` (CloudFormation), `scripts/` (tooling), `.github/workflows/` (CI and deploy), `.factorial/` (settings Factorial reads from any target, here its own). See `README.md`.
- **Workflows:** six rules, enforced by `scripts/check-workflows.ts`: (1) a job assuming the deploy role declares `environment: production` and the full trust gate in its `if:` (`classify` and `deploy` in `deploy.yml` are the reference); (2) every remote `uses:` is pinned to a 40-character SHA; (3) no Actions cache; (4) a job using `./.github/actions/classify-changes` or `git diff`/`log`/`merge-base` checks out with `fetch-depth: 0`; (5) `ci.yml` keeps the job names `Typecheck, test and lint` and `Lint CloudFormation`, required by the `main` ruleset; (6) the `stacks=(...)` list in the "Deploy stacks in order" step of `deploy.yml` names every `templates/<name>.yml` except `foundation.yml`, exactly once each (order is not checked).
- **Checks:** `npm run ci` (typecheck, build with every bundle checked to load as a module, tests, `.yml` extension check, `check:workflows`, cfn-lint); CI runs the same on every push and PR.
- **Artefacts:** every stage writes to `<workItemId>/<attempt>/<stage>/` through `@factorial/artefacts` (`putArtefact`, which redacts; `putBinaryArtefact` only for the git bundle). Uploads are idempotent and the bucket is versioned; deletes are denied to every principal and retention is the `ArtefactRetentionDays` lifecycle rule. Only orchestrator Lambdas and the invoker write (`s3:PutObject`); the orchestrator reads back only named keys it wrote, each granted explicitly (a reporter reads only `report.json`); no agent role reaches the bucket. The ledger holds the prefix, never content.
- **Correlation:** the work item id is the Runtime session id, ledger key, artefact prefix and `workItemId` on every log line (via `@factorial/log`) and state output; the ledger row records the execution's ARN (`executionArn`), since EventBridge names the execution. Every component carries it, and `docs/finding-a-run.md` must keep reaching every record.
- **Non-functional paths:** `scripts/classify-changes.ts` is the single list of paths that cannot affect a deploy (`docs/**`, `README.md`, `CLAUDE.md`, `LICENSE`, `.editorconfig`, `.github/CODEOWNERS` and similar). CI takes a fast path for PRs that change only those, and the deploy skips when nothing else changed since `FactorialVersion`. Everything else is functional by default.
